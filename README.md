### Туршилтын тохиргоо

Collection-ийн `baseURL` хувьсагчид энэ утгыг тохируулсан.

## API-ийн бодит ажиллагаа

Энэ спецификаци нь өгсөн `server.js`-ийн хэрэгжүүлэлтэд үндэслэв. Тестлэгдэх endpoint: `POST /registrations`.

- Бүртгүүлэх хүсэлт зөвхөн `studentID`, `courseID` талбар шаарддаг.
- `coursesTaken` нь `PUT /students/:id` setup хүсэлтээр хадгалагдана. Setup-д энэ талбарыг орхивол `[]` болно; үүнээс болж `400` буцаахгүй.
- Хичээлийн `prerequisites` нь `PUT /courses/:id`-аар хадгалагдана. Орхивол `[]` болно.
- Амжилт: HTTP `201`, `result: "OK"`, шинээр үүссэн `registrationID`.
- Бизнесийн дөрвөн алдаа: HTTP `200` ба харгалзах `ERROR_*`.
- `studentID` эсвэл `courseID` дутуу буюу falsy утгатай бол HTTP `400`, `ERROR_BAD_REQUEST`.
- Шалгалтын дараалал: JSON задлах → шаардлагатай ID-ууд → оюутан байгаа эсэх → `status === "active"` → хичээл байгаа эсэх → урьдач нөхцөл. Эхний илэрсэн алдааг буцаана.
- JSON буруу бүтэцтэй бол HTTP `400`, `ERROR_BAD_JSON` (доорх үндсэн 12 спецификациас тусдаа).

### Сонголт ба төлөөлөх утгууд

Доорх урьдачийн жишээнд хичээлийн `prerequisites = ["C101", "C102"]` гэж үзэв.

| Шалгах шинж               | Сонголт           | Төлөөлөх утга                       |
| ------------------------- | ----------------- | ----------------------------------- |

| Оюутны төлөв              | Идэвхгүй          | `status: "inactive"`                |
| Оюутны хүчинтэй байдал    | Байхгүй           | Setup-аар үүсгээгүй оюутны ID       |
| Үзсэн хичээлүүд           | Урьдач хангана    | `coursesTaken: ["C101", "C102"]`    |
| Үзсэн хичээлүүд           | Урьдач хангахгүй  | `coursesTaken: ["C101"]`            |
| Хичээлийн хүчинтэй байдал | Байгаа            | PUT setup-аар үүсгэсэн хичээлийн ID |
| Хичээлийн хүчинтэй байдал | Байхгүй           | Setup-аар үүсгээгүй хичээлийн ID    |
| Урьдач нөхцөл             | Бүгд үзсэн        | `coursesTaken: ["C101", "C102"]`    |
| Урьдач нөхцөл             | Огт үзээгүй       | `coursesTaken: ["C050"]`            |
| Урьдач нөхцөл             | Заримыг үзсэн     | `coursesTaken: ["C101"]`            |
| Хязгаарын утга            | Үзсэн хичээлгүй   | `coursesTaken: []`                  |
| Хязгаарын утга            | Урьдач нөхцөлгүй  | `prerequisites: []`                 |
| Хүсэлтийн бүтэц           | `courseID` дутуу  | `{"studentID":"SP10_student"}`      |
| Хүсэлтийн бүтэц           | `studentID` дутуу | `{"courseID":"SP12_course"}`        |

**Хамаарал:** “Урьдач хангана” болон “Бүгд үзсэн” нь нэг нөхцөлийн хоёр илэрхийлэл. “Огт үзээгүй”, “Зарим нь” нь хоёулаа “Урьдач хангахгүй” ангилалд орно. Иймээс эдгээрийг үл хамаарах сонголт мэт бүх боломжит хослолоор үржүүлэхгүй. Урьдач нөхцөлгүй хичээлд хоосон `coursesTaken` байсан ч урьдач хангана. Байхгүй оюутан/хичээлд хамаарах үнэлгээг `—` гэж тэмдэглэв.

### Initialization ба тестийн бие даасан байдал

Спецификацийн хүснэгт дэх `S001`, `C201` зэрэг нь логик жишээ ID юм. Бодит collection-д тестүүдийг тусгаарлахын тулд `SP01_student`, `SP01_course` зэрэг тест тус бүрийн ID ашигласан.

Тест бүр өөрт шаардлагатай оюутан болон хичээлийг PUT setup хүсэлтээр бэлтгээд, дараа нь `POST /registrations` хүсэлтээ илгээнэ. PUT хүсэлт нь ижил ID-тай бичлэгийг дахин бичдэг тул setup-ийг давтан ажиллуулах боломжтой.

| Спецификаци                              | Өөрийн setup                                                   |
| ---------------------------------------- | -------------------------------------------------------------- |
| SP01, SP02, SP04, SP07, SP08, SP09, SP11 | Оюутан болон хичээл үүсгэх PUT хүсэлтүүд                       |
| SP03, SP10                               | Оюутан үүсгэх PUT хүсэлт                                       |
| SP05, SP12                               | Хичээл үүсгэх PUT хүсэлт                                       |
| SP06                                     | Setup хэрэггүй; оюутан болон хичээл хоёулаа байхгүй байх ёстой |

Байхгүй ID шалгах тестүүдийн тухайн ID-г бусад setup хүсэлтээр үүсгэхгүй. Folder бүрийг setup хүсэлтүүдтэй нь хамт ажиллуулах бөгөөд өөр folder-ийн үүсгэсэн өгөгдөлд найдахгүй.

### Oracle буюу хүлээгдэх үр дүнгийн шалгалт

PUT setup хүсэлт бүр HTTP `200`, `result: "OK"` буцаах ёстой. Үндсэн POST хүсэлтэд спецификацид заасан HTTP статус болон `result` утгыг шалгана.

| Спецификаци               | Нэмэлт шалгах утга                      |
| ------------------------- | --------------------------------------- |
| SP01, SP08                | `registrationID` нь тоо байна           |
| SP02, SP09                | `missing` нь `["C101", "C102"]` байна   |
| SP11                      | `missing` нь `["C102"]` байна           |
| Алдааны бусад тохиолдлууд | Хариунд `registrationID` талбар байхгүй |

Серверийн бүртгэлийн жагсаалт ажиллуулах явцад хуримтлагддаг тул `registrationID`-ийн яг утгыг шалгахгүй. Тест бүрийн өмнө серверийг дахин асаах шаардлагагүй бөгөөд амжилтын oracle нь `registrationID` тоон төрөлтэй эсэхийг шалгана.

Доорх тоонуудыг `results/` хавтас дахь бүтэн текст log-ийн төгсгөлийн хүснэгт болон `exit=` мөрөөс авсан.

| Ажиллуулалт     | Iterations executed | Requests executed | Requests failed | Assertions executed | Assertions failed | Exit code |
| --------------- | ------------------: | ----------------: | --------------: | ------------------: | ----------------: | --------: |
| PASS            |                   1 |                30 |               0 |                  48 |                 0 |         0 |
| FAIL            |                   1 |                30 |               0 |                  48 |                 1 |         1 |
| DOWN            |                   1 |                30 |              30 |                  48 |                48 |         1 |
| Нийтийн API GET |                   1 |                 1 |               0 |                   3 |                 0 |         0 |

Үндсэн collection-ийн нэг ажиллуулалтад Newman-аар тоологдсон тестийн тоо буюу `assertions executed` нь **48**. Спецификацийн тоо, HTTP хүсэлтийн тоо, assertion-ы тоо нь өөр ойлголтууд юм.

Нийтийн API-ийн GET тестийг тусдаа ажиллуулсан бөгөөд түүний **3 assertion** нь үндсэн PASS log-ийн **48 assertion**-д ороогүй.

### PASS

Үндсэн зөв collection-ийг сервер асаалттай үед ажиллуулахад 48 assertion бүгд тэнцэж, failed нь 0, exit code нь 0 гарсан.

### FAIL

Тусдаа `lab05-collection-fail.json` collection-ийн SP01 oracle-д амжилтын HTTP статусыг зориуд `201`-ийн оронд `200` гэж хүлээхээр өөрчилсөн. Сервер `201` буцаасан тул 48 assertion-оос 1 нь унаж, exit code 1 гарсан.

Log-д `expected response to have status code 200 but got 201` гэсэн алдаа бүртгэгдсэн. Үндсэн зөв collection-ийн oracle-ийг өөрчлөөгүй.

### DOWN

Серверийг унтраагаад үндсэн collection-ийг ажиллуулахад 30 хүсэлт бүгд холбогдож чадаагүй бөгөөд `connect ECONNREFUSED 127.0.0.1:3000` гэсэн алдаа гарсан. Хариу ирээгүйгээс 48 assertion бүгд унаж, exit code 1 гарсан.

FAIL нь ирсэн хариу oracle-ийн хүлээлттэй зөрсөн тохиолдол, харин DOWN нь сервертэй холбогдож чадаагүй интерфейсийн алдаа юм.

### CI quality gate

Exit code 0 нь энэ ажиллуулалтын шалгалтууд амжилттай дууссаныг, exit code 1 нь алдаа илэрснийг илэрхийлнэ. CI quality gate нь ийм exit code-д үндэслэн дараагийн шат руу үргэлжлүүлэх эсэхийг шийдэж болно.

Тестийг дахин ажиллуулж log шинэчилсэн тохиолдолд энэ хүснэгтийн тоонуудыг мөн шинэчилнэ.

## 7. Дүгнэлт

Тестийн дизайны таван алхмаас сонголтуудыг хослуулж, төлөөлөх спецификаци сонгох хэсэг хамгийн их бодол шаардсан.
Учир нь сонголтууд хоорондоо хамааралтай тул бүх хослол бодит нөхцөлийг илэрхийлэхгүй байсан.
Тухайлбал, урьдач хичээлтэй үед “урьдач хангана” болон “заримыг үзсэн” гэсэн сонголтыг хамтад нь авах боломжгүй.
Мөн бүртгэлгүй оюутанд үзсэн хичээлийн төлөв оноож урьдачийг үнэлэх нь утгагүй байсан.
Тестүүдийг бие даалгахын тулд шаардлагатай өгөгдлийг тухайн тестийн PUT setup-аар бэлтгэж, тусдаа ID ашигласан.
Үндсэн PASS ажиллуулалтын 48 assertion бүгд тэнцсэн тул шалгасан хүрээнд API-ийн бизнес логикийн согог илрээгүй боловч энэ нь бүх боломжит оролтод согоггүй гэсэн баталгаа биш.
Харин collection export хийхэд `baseURL` хоосон үлдсэн тестийн тохиргооны алдааг илрүүлж зассан.
Зориуд буруу болгосон oracle нь FAIL ажиллуулалтад нэг assertion унагаж, exit code 1 өгсөн нь шалгалт зөрүүг илрүүлж байгааг харуулсан.
Сервер унтарсан DOWN ажиллуулалтын `ECONNREFUSED` нь oracle-ийн хүлээлтийн зөрүүнээс ялгаатай холболтын алдаа болохыг ажигласан.
Ингэснээр тестийн үр дүнг зөв тайлбарлахын тулд assertion-ы тоо, алдааны шалтгаан, exit code болон бүтэн log-ийг хамтад нь авч үзэх шаардлагатайг ойлгосон.
